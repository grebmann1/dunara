# Supabase provider contract and evidence

Updated September 17, 2026 for S0–S8. All remote endpoints below remain **unqualified against a live Supabase account**. Official documentation establishes the candidate contract; controlled responses establish local parsing, redaction and error behavior. Neither establishes the permissions or delivery behavior of a real account.

## Credentials and capability reporting

Current Builder connections use a manually supplied management personal access token, held in backend memory or encrypted storage. App publishable keys and Builder account JWTs are separate credentials. Management OAuth also has a hosted, encrypted, account-authorized broker; registration and live grants remain unqualified. Token prefixes are not used to infer granted permissions.

`backend_capabilities` checks organization/project listing and, after verifying the selected binding's reference and organization, project health, Auth configuration readability and migration history. It returns permission observations, prerequisites and redacted resource identity. It does not expose Auth configuration values, API keys, SQL history, or app-user records. It does not probe writes or reveal project secrets to determine access. Scope metadata and remote write permissions stay `unknown`; successful reads only establish the individual read permission at the time recorded. See the [scope reference](https://supabase.com/docs/guides/integrations/build-a-supabase-oauth-integration/oauth-scopes).

## Bounds, rate limits and local paging

Provider response streams are capped at 2 MB before parsing. Unexpected JSON shapes and missing required fields produce sanitized `PROVIDER_RESPONSE_INVALID`, never raw schema issues or provider bodies. Mutation responses without a valid required identity produce `RECONCILIATION_REQUIRED`. Empty JSON read results still have to match that endpoint's schema. A void mutation may return an empty successful body.

GET requests retry HTTP 429/502/503 at most twice, with bounded delay; a numeric `Retry-After` greater than two seconds returns a rate-limit prerequisite. Each request has a 30-second timeout. HTTP 401 asks for reconnection; 403 reports denied permission; 429 asks the caller to wait. Fixed production quotas and date-form `Retry-After` behavior are not qualified. Writes are never retried automatically. The durable Builder request ID prevents duplicate local submissions; it does not establish provider-side idempotency for a POST.

The organization/project endpoints currently document whole arrays. Builder fetches these under its hard limits and pages the validated snapshot locally: 50 rows per collection by default, maximum 100. `pagination` discloses both totals, `truncated` and `nextOffset`. Subsequent calls require the previous `revision`; connection or snapshot changes fail with `REVISION_CONFLICT`. Over-limit provider arrays fail rather than silently truncating. All catalog calls require a local project ID. Duplicate display names are allowed; users and agents must select a specific organization and reference. Studio leaves both choices empty after loading.

### Exact added transport contracts

- Auth PATCH supports explicit public email/SMTP/Google fields and separate private `smtp_user`, `smtp_pass`, `external_google_secret` values. Google nonce bypass is always false. [Google configuration and callbacks](https://supabase.com/docs/guides/auth/social-login/auth-google) remain a separate app-login flow from management OAuth.
- Storage uses `GET /storage/v1/bucket/{id}`, `POST /storage/v1/bucket` and `PUT /storage/v1/bucket/{id}` with a modern server secret in `apikey`. Only private standard buckets with bounded MIME/size settings are accepted. No arbitrary metadata SQL, public toggle, empty or delete action is exposed. See [Storage API](https://supabase.com/docs/reference/self-hosting-storage) and [modern API keys](https://supabase.com/docs/guides/getting-started/api-keys).
- Function deployment uses `POST /v1/projects/{ref}/functions/deploy?slug=...`, multipart `metadata` and `file` parts. It validates ID/slug/version/status/verify_jwt, then compares a separate list readback and requires an increased version for replacement. Secret binding uses `POST /v1/projects/{ref}/secrets` with name/value pairs resolved only at dispatch. See [deploy](https://supabase.com/docs/reference/api/v1-deploy-a-function) and [bulk secrets](https://supabase.com/docs/reference/api/v1-bulk-create-secrets). These are writes with no automatic retry.
- OAuth token/refresh exchanges use the registered client and PKCE against `/v1/oauth/token`. Revocation uses JSON `client_id`, `client_secret`, `refresh_token` at `/v1/oauth/revoke`, as specified by [the revocation endpoint](https://supabase.com/docs/reference/api/v1-revoke-token). Tokens remain encrypted on the hosted broker; desktop receives only authenticated one-use completion/public connection metadata.

See [the operating guide](supabase-configuration.md) for deployment settings and individually tracked release gates. No exact scope set is advertised as verified against a real account.
