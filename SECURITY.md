# Security and trust

## Intended deployment

This is a **trusted, single-user local development tool**, not a security sandbox or multi-tenant service. The studio binds to IPv4 loopback. Do not expose it through a reverse proxy, public tunnel, or shared machine account.

`--trust-execution` is a local operator decision. Without it, preview execution and managed dependency installation fail with `TRUST_REQUIRED`. MCP and studio requests cannot turn it on. Once enabled, generated code, Metro configuration, and dependencies can execute with your user privileges and inherited environment. Do not run unreviewed projects or provide the process with unnecessary credentials.

The harness itself may have broader filesystem/shell permissions than these tools. Configure those separately; builder boundaries do not constrain external harness tools.

## Controls

- Registered canonical project roots, symlink rejection, bounded source reads/listings, and blocked secret/dependency paths.
- SHA-256 expected revisions; batch prevalidation, serialized in-process mutations, and per-file atomic replacement. A batch is **not** an all-or-nothing filesystem transaction. Failure details identify applied files.
- Fixed process argument arrays, curated manifest/lock checks, and `npm ci --ignore-scripts --no-audit --no-fund`. Already-installed dependencies are not cryptographically re-attested. This is not dependency isolation.
- Owned preview-process tracking, bounded concurrency/logs, cancellation, deadlines, and graceful shutdown. No persisted PID is trusted after restart. Force-killing the CLI, power loss, and deliberately daemonizing code are outside graceful-cleanup guarantees.
- Studio Host/Origin validation, no permissive CORS, a 60-second single-use fragment bootstrap ticket, and per-runtime bearer authentication for APIs and WebSocket upgrades. No bearer token is placed in the iframe. Logs must not include launch tickets or authorization headers.
- Generated app content uses a separate origin and a constrained iframe. The Expo development server itself is not an authenticated production app server.
- Captures accept validated app paths on a managed preview only, block external network origins and redirects, and expire bounded in-memory PNG artifacts.

Local malware, malicious browser extensions, hostile same-user processes, and filesystem races caused by an adversarial process are not covered. Use one runtime per workspace/home pair: registry and write serialization are process-local, not cross-process locks.

## Optional creative media boundary

OpenAI credentials can come from startup `OPENAI_API_KEY`/`BUILDER_ASSISTANT_API_KEY`, the explicit Dunara `.env` (`--builder-env-file`), or masked entry in authenticated Studio Settings. Opt-in **Remember on this computer** persists one shared OpenAI key for Assistant and image generation in an AES-256-GCM encrypted owner-only Dunara-home file (0700 directory, atomic 0600 files), with slot-bound authenticated context. Desktop wraps the master key using OS safeStorage; headless mode requires the explicitly configured encryption key. Linux basic_text fallback is rejected. Legacy plaintext is removed only after encrypted read-back succeeds; locked data is retained without silent fallback. Storage rejects unsafe owner/mode/type/link/size/schema conditions; same-user processes remain within the trust boundary; encryption is not an execution sandbox. See `docs/credentials.md`. Browser entry necessarily holds the secret transiently and sends it to the server; the field clears on submission, completion/failure, cancel and navigation/unmount. The server keeps providers in private process memory, never returns a key/suffix/fingerprint, and persists no UI credential in browser storage, project/job files, or `process.env`. Shutdown releases active/startup provider references, without claiming reliable JavaScript memory zeroization. Both supported OpenAI variables remain filtered from managed generated-app environments; the Assistant worker receives only its selected key for the active turn. Do not use `VITE_` or `EXPO_PUBLIC_` variables, source, prompts, chat or generated-app `.env` files for credentials. The CLI does not search old credentials. A malicious process with your privileges can still access local resources: filtering an environment variable is not isolation.

Settings uses authenticated GET/POST at `/api/settings`, exact Host/Origin checks, no query credentials, no-store responses, strict action schemas, an 8 KiB JSON body limit and rejection of compressed credential bodies. Malformed/invalid values yield sanitized errors without reflecting input. Keys are trimmed, then bounded to 4096 non-whitespace printable ASCII characters without a hard-coded prefix. Only configured/source/opaque revision/busy/environment-availability status is returned; broadcasts contain a generic change signal. There is no MCP credential-setting or credential-readback tool.

A session provider overrides startup configuration. Disconnect disables generation even if a startup provider exists; restoration is explicit. Saved values take precedence over startup keys. Session-only replacement and disconnect delete saved values. Restart forgets session changes and restores saved/startup configuration; remove startup keys as well for lasting disconnection. Settings changes and paid approvals share the media serialization queue. Changes reject stale revisions and queued/running or still-settling work; paid approval requires the currently disclosed configuration revision, so old consent cannot silently spend with a replacement provider. Saving never probes OpenAI, verifies an account, retries a request or grants spending permission. Concurrent tabs must re-review after a configuration change.

Image generation/editing calls OpenAI only after explicit authenticated Studio approval of each request's model, prompt, reference images, output count, size and quality. Source/brief/library are not automatically sent. MCP may stage but cannot approve a billable request; execution trust is separate. Provider approval is an application workflow for a trusted single user, not a protection against an external harness with unrestricted shell/browser access. Costs are not precisely estimated, automatic SDK/billable retries are disabled, and cancellation or shutdown does not guarantee provider-side cancellation or a refund. A request may incur charges before an output/revision failure. Raw provider errors are not forwarded to diagnostics.

Project assets use a dedicated revisioned manifest and immutable normalized PNGs under `assets/builder/`; text-file tooling is not broadened to arbitrary binary writes. Imports permit only single-frame PNG/JPEG/WebP, bounded to 10 MiB and 16 megapixels, with metadata stripped. Reads validate manifest paths, hashes, sizes and image properties; symlinks/root changes are rejected. Quotas are 100 versions/100 MiB per project, including orphan-file accounting. There is no arbitrary-URL download or automatic deletion of referenced assets. Studio images and binary uploads require the existing exact Host/Origin and bearer checks; the dedicated upload bound does not raise the normal 1 MB JSON limit.

Prompts, reference IDs, permissions and job results persist under builder home in `media-jobs.json`, not inside the generated app asset tree. Protect this home as potentially sensitive data. The ledger retains at most 100 jobs, ten pending requests and one provider call at a time. Queued/running work is interrupted on restart, never silently resubmitted. Credentials are prohibited in job records; opt-in saved keys use the separate private credential store. Local asset/library operations remain available without a provider key. The application strips metadata, but does not certify image rights, provider compliance, visual accuracy or content safety.

Icon application displays a config diff and requires confirmation plus matching media/config/proposal revisions. It changes only the selected project's `app.json`, preserves unrelated settings, refuses overriding dynamic configuration and does not execute config code. MCP's confirmation flag relies on the harness obtaining actual user confirmation. Native launcher/store acceptance remains unverified until a real build/device review. See `docs/media-workflow.md` for operator details.

## Preview context inspection

Inspection preserves the separate-origin iframe sandbox, Studio authentication, CORS and CSP. A development-only embedded Expo web bridge pins its actual parent at an exact validated loopback origin; Studio checks the iframe sender, managed preview origin, strict versioned schema and per-frame nonce. Messages are bounded JSON strings (32 KiB); commands contain no credentials, project filesystem root or privileged endpoint capability. The bridge has no fetch, clipboard, file-write, expression-evaluation or generic DOM-command interface. Native, standalone development and production contexts are inactive.

Copied context is limited to 16 KiB and uses safely quoted JSON with formatting delimiters escaped. Studio supplies project identity; app-reported observations and explicit source annotations remain untrusted and annotations are unverified. No source ownership is inferred from React internals. Raw HTML, editable/password values (including descendants of selected containers), cookies/storage/headers, query/hash and image URLs are excluded. Ordinary visible text and the Studio-supplied project root can still reveal personal information: review before external pasting. Neither exclusion nor quoting guarantees complete redaction or immunity to prompt injection in an external harness.

Copying requires a direct Studio user gesture, never an iframe message. Frame/project/navigation/workspace lifecycle changes invalidate selections. Existing-project setup requires a displayed proposal, explicit confirmation, exact recomputed proposal hash and existing revision/root protections. It only installs canonical helpers plus a marked layout import; conflicts refuse automatic changes. Partial batches report applied files and require fresh review before retry. Selecting a project or starting a preview never silently changes source. See `docs/preview-context.md` for the supported layouts, protocol and limitations.

## LAN opt-in

`--lan` additionally requires execution trust and deliberately exposes Expo on the local network for Expo Go. Use it only on a trusted network. The studio stays loopback-only. Device URLs are shown only if Expo emits them; the builder does not guess a usable device endpoint. LAN/native-device execution has not been runtime-verified in this implementation.

## Reporting

There is no public repository, security email, or private advisory channel configured yet. Report a suspected issue privately to the person or organization that supplied this source, using an existing verified contact. Do not publish secrets, real project content, authorization tokens, or weaponized exploit details. Include a minimal temporary-workspace reproduction, platform/version, expected boundary, and observed behavior.

A public release should establish a maintained private reporting channel and complete the outstanding checks in `docs/verification.md`. No security audit certification or response SLA is claimed.
